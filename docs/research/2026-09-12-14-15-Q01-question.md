**Topic:** Best practices for coordinating five heterogeneous coding agents (and the humans driving them) through GitHub Issues and the `gh` CLI during a time-boxed hackathon — what to keep, what to cut, and what to harden in an existing "Issues as task board + negotiation channel" protocol.

## Context

### Project Background

We are a five-engineer team at an in-person, one-day AI hackathon (10 a.m.–4 p.m. ET submission close; at time of writing there are roughly 100 minutes left). We sit at one table with laptops. Each engineer drives their own AI coding agent, and the harnesses and models differ by person: at least Claude Code (Anthropic's CLI agent) and "Pi" (another teammate's coding-agent harness); others may use Cursor-style IDE agents. Every agent has the GitHub CLI (`gh`) installed and authenticated **as its human** with write access to one shared public repository. That repository is the only shared medium the agents have in common — agents cannot hear the humans talk across the table.

The project itself (a browser-based desktop OS whose AI agent authors and installs apps at runtime) is organized into five parallel workstreams that map to architectural "slices" (OS shell/window manager; agent chat + tool calling; runtime component engine; persistence/virtual filesystem; integration + demo apps) plus a sixth "docs" workstream (ADRs, README, submission writing). The seams between slices — e.g., the chat tool handler that must call the filesystem API and the window opener — are where parallel work collides.

Repository conventions already in force (non-negotiable for the answer):

- Docs-first: architecture decisions are MADR 4.0 ADRs with YAML frontmatter following Google's Open Knowledge Format (OKF v0.2: `type`, `title`, `description`, `tags`, `generated`, `verified`, `sources`, `stale_after`), 80-column markdown enforced by markdownlint in a pre-commit hook and CI.
- Small PRs into `main`, merged quickly by the repo owner; CI runs markdown lint only during the sprint (type-checking gates deliberately deferred).
- Agent-facing guidance lives in `docs/agents/` as OKF "playbook" documents that agents are pointed to.

A coordination protocol ("v1") was just introduced by one teammate as a repo-local skill plus a bash script wrapping `gh`. Its design, which the research should critique rather than re-invent:

1. **Assignment is the lock.** An issue with an assignee is owned; the script refuses to claim an owned issue. Same-second claim races are resolved by the earliest `CLAIM` comment; the loser's script auto-unassigns and posts a `RELEASE`.
2. **Labels are the state machine.** `ws:<workstream>` (six values), `status:{unclaimed,claimed,in-progress,blocked,in-review}`, priority `p0`–`p2` where `p0` means "on the demo golden path", `type:{task,contract,decision,bug}`, `needs-human` (escalation), and `hub` (one pinned coordination issue).
3. **Structured comments are the conversation.** Every protocol comment opens with a header line: `**VERB** | agent: <producer/version> | human: @<login> | at: <ISO-8601 UTC>` followed by a body. Verbs: CLAIM, RELEASE, STATUS, BLOCKED, UNBLOCKED, QUESTION, ANSWER, PROPOSE, ACCEPT, COUNTER, REJECT, HANDOFF, REVIEW, DONE, DEP-DONE (script-posted), SYNC (hub only). Agents parse history with `gh --jq` on `startswith("**CLAIM**")` etc.
4. **Parameters:** stale claim = no heartbeat verb (CLAIM/STATUS/UNBLOCKED/HANDOFF) for 45 minutes, releasable by anyone; negotiation cap = the fourth PROPOSE/COUNTER adds `needs-human` and @-mentions every human involved; STATUS expected roughly every 30 minutes; at most two claims per agent.
5. **Cross-slice interfaces** go on `type:contract` issues; code is built only after `ACCEPT`, which appends the accepted proposal to the issue body under an "Agreed" heading so the contract is readable without scrolling comments.
6. **Issue body template:** Goal / Done when (checkboxes) / Files (globs, used as the overlap check on the board) / Depends on (`#n`; `done` posts `DEP-DONE` on dependents) / Notes / Agreed.
7. **Hub issue:** one pinned issue that accepts only `SYNC` one-liners ("on / blocked / next"); `sync` at session start prints the board, one's own claims, stale claims, `needs-human` items, and the last five SYNC lines.
8. **Fallback for agents that cannot run bash:** raw `gh issue comment` / `gh issue edit` commands that reproduce the header line and label transitions by hand.

Hardware, infrastructure, and budget are irrelevant here: everything runs through GitHub's hosted Issues and each person's `gh`. No new infrastructure (no chat bots, no external boards, no servers) may be introduced. GitHub Projects (v2) was considered and skipped because it requires an extra OAuth scope on every teammate's token.

### Specific Situation

We must make two decisions in the next hour and one durable decision for the team:

1. **Sprint-minimum ceremony.** Which of the verbs, rituals, and parameters above pay for themselves inside a two-to-four-hour co-located sprint, and which burn clock? A review of the protocol already raised that STATUS-every-30-minutes, contracts-before-code, and plan/ETA on every claim may be right-sized for a day and heavy for 100 minutes. We need a defensible "today" subset and a rationale we can state in one paragraph.
2. **Parameter values.** Is a 45-minute stale timer, a four-round negotiation cap, and a two-claim limit defensible, and what evidence or analogy supports different values for a sprint versus a multi-day project?
3. **The hardened playbook (durable).** A `docs/agents/coordination-best-practices.md` document — short enough for an agent to read in three minutes at session start — that tells every agent, regardless of harness or model, how to behave so that the classic multi-agent failure modes do not happen: duplicated work, guessed interfaces at slice seams, silent or stale claims, merge conflicts on shared files, agents negotiating past the point of information, and humans losing sight of the board.

"Success" is a set of concrete, cited recommendations that we can adopt as a v1.1 of the protocol (a diff against the design above), plus the playbook text. We will implement the recommendations by editing the skill's documentation and script parameters and by publishing the playbook; we will not build new tooling.

### What We've Tried or Considered

- **Free-text issue comments** were rejected because heterogeneous agents cannot reliably parse them; the bold-verb header line exists to make history machine-readable with `gh --jq`. Do not recommend abandoning structure.
- **GitHub Projects (v2) boards** were skipped for token-scope friction; if the evidence says Projects is decisively better even so, say it, but assume Issues + labels is the default.
- **Talking across the table** is the cheapest coordination channel for the humans, but the agents cannot hear it. An unresolved question is what *must* be written into Issues (so agents that were not in the conversation have it) versus what should stay verbal.
- **Ceremony concern**: already raised, not yet resolved — see decision 1.
- **Stale-release concern**: in a sprint a human is often heads-down for 45 minutes while their agent is idle, so a teammate's issue could be released mid-flight; harm is low because assignment is a coordination signal, not a code lock, but it erodes trust in the board. A "ping with QUESTION, then release if unanswered" courtesy was suggested.
- **Locked decisions the research should not revisit:** `gh` + Issues as the only channel; small PRs into `main`; the owner merges; OKF frontmatter and 80-column markdown for all docs; the six-workstream split; the bold-verb header format (parameters and verb *set* may change, the header shape should not).

## Research Question

For a co-located team of five engineers whose heterogeneous AI coding agents coordinate exclusively through GitHub Issues and the `gh` CLI during a ≤4-hour hackathon, what does the best available evidence — from multi-agent software-engineering research, from open-source maintainers' long-standing issue-tracker and label conventions, from practitioner reports of agent fleets working GitHub issues (including GitHub's own Copilot coding agent), and from coordination and concurrency theory — say about:

- **(a) Minimum viable ceremony.** Which coordination primitives (claiming with a plan, periodic status heartbeats, contract-before-code on interfaces, structured negotiation verbs, a pinned sync hub, file-glob overlap declarations) have the best cost/benefit under extreme time pressure, and which should be optional or dropped for a sprint? Give a "sprint-minimum" protocol and a "full" protocol, with the switch condition between them.
- **(b) Cross-harness parsability and identity.** How should assignment-as-lock, labels-as-state, and structured comments be designed so that agents built on different models and harnesses (some unable to run shell scripts) interoperate reliably? Include actor identification when two humans' agents share the same model identifier.
- **(c) Parameters.** What stale-lock timeout, negotiation-round cap, heartbeat cadence, and per-agent claim limit are defensible for a sprint, and by what reasoning or precedent (e.g., lease durations in distributed locking, WIP limits in Kanban, escalation ladders in incident response)?
- **(d) Integration cadence.** What branch, PR-size, review, and merge cadence keeps five parallel streams integrable into one working demo within hours — including how to handle the shared "kernel" files that several slices touch, and whether an explicit integration checkpoint is worth its cost?
- **(e) Failure modes and defenses.** Which documented failure modes of LLM-agent teams (duplicated work, hallucinated or guessed interfaces, infinite negotiation, silent stalls, over-claiming, premature "done", context loss on handoff, rate-limit storms against the GitHub API) apply here, and what specific defenses — protocol rules, script checks, human rituals — have evidence or strong practitioner consensus behind them?
- **(f) Human-in-the-loop design.** When should agents stop and escalate to humans (`needs-human`), how should escalations be surfaced so co-located humans actually see them within minutes, and what must be written into Issues (versus said aloud) so agents that were not in the room stay correct?

State explicitly where the evidence is thin and you are reasoning from analogy.
